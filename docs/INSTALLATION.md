# Installation and upgrades

## Deploy button

The README button opens Cloudflare's repository deployment flow. It requires a Cloudflare account, GitHub authorization, and permission to create a repository and app resources. Cloudflare documents the flow and automatic provisioning in [Deploy to Cloudflare buttons](https://developers.cloudflare.com/workers/platform/deploy-buttons/).

Enter `SETUP_PASSPHRASE` as a secret when prompted. Use at least 16 characters and keep it private. Retain the default build/deploy scripts so D1 migrations run before the Worker is published. Open the assigned `workers.dev` URL and complete `/setup`.

Setup creates one admin and empty starter rooms. It closes after success, including after redeployments. The setup passphrase is not your login password.

If setup reports missing tables, check the deployment log for the D1 migration command and confirm the `DB` binding points to the provisioned database. If the secret is missing, add `SETUP_PASSPHRASE` under your Worker's Settings → Variables and Secrets and redeploy.

## Manual deployment

```sh
npm ci
npx wrangler login
npx wrangler d1 create extb-community
```

Copy the returned database ID into `wrangler.toml`, replacing the placeholder. Keep the binding named `DB`. Set the Worker `name` to your chosen app name if needed.

```sh
npx wrangler secret put SETUP_PASSPHRASE
npm run deploy
```

Open the deployment URL, visit `/setup`, and create your owner account. No `PASSWORD_SALT` or `CHAT_DO_SECRET` entry is required for a new installation. Account salts and private chat authentication material are generated by the app. A second SQLite Durable Object, `PasswordHasher`, performs password hashing through internal RPC so the Worker keeps authentication within its Free-plan request CPU budget. It does not store passwords or hashes.

## Local development

Copy `.dev.vars.example` to `.dev.vars` and set `SETUP_PASSPHRASE`. Run `npm run db:local`, then `npm run dev`. Local D1 data lives in Wrangler's ignored state directory. Never commit local data or secrets.

## Optional services

Add secrets through the Cloudflare dashboard or `wrangler secret put`. Add public configuration through Wrangler's `[vars]` table or the dashboard.

| Capability | Configuration |
| --- | --- |
| Public email registration and recovery | `BREVO_API_KEY` secret, `EMAIL_FROM_ADDRESS` verified sender, optional `EMAIL_FROM_NAME` |
| Canonical address | `COMMUNITY_ORIGIN`, such as `https://community.example.com`, with no path |
| Registration and login CAPTCHA | `TURNSTILE_SITE_KEY` and `TURNSTILE_SECRET`; configure permitted hostnames in Turnstile |
| Browser push notifications | `VAPID_PUBLIC_KEY` and `VAPID_PRIVATE_KEY` |
| Image storage | Optional `MEDIA` R2 binding; see [uploads](UPLOADS.md) |

Email registration also respects the `signups_open` setting in Admin → System → Settings. Verify your sender with Brevo before enabling email registration. Without an email provider, registration uses admin invitations. Invites expire after seven days and can be redeemed once. Email verification does not block invited members.

Keep a working HTTPS origin when sending email. The app derives it from the installation request when no explicit origin is configured. For a custom domain, configure it in Cloudflare first, then set `COMMUNITY_ORIGIN`.

## Updates

Back up D1 before upgrading. Cloudflare provides [D1 Time Travel](https://developers.cloudflare.com/d1/reference/time-travel/) and database export tools. Preserve any R2 uploads separately.

Review upstream changes, merge them into your repository copy, run `npm ci` and `npm run verify`, then deploy with your existing configuration. Keep the same Worker name, D1 database ID, `DB` binding, `CHAT_ROOM` and `PASSWORD_HASHER` bindings, and both Durable Object classes. Use `npm run deploy:uploads` if your installation uses the optional uploads configuration.

For Workers Builds, keep the build/deploy command aligned with the configuration you use. Changing back to the core configuration removes the upload binding, so upload controls disappear until the binding is restored.

Never reinitialize a production database, delete its migration history, or replace its binding with a new empty database during an upgrade.
